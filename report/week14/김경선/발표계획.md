## 1페이지 — advisord + priors (55초)

**스크린샷 배치:** 화면 좌우 또는 상하로 두 장 나란히

**advisord 화면:**
```
$ advisord
advisord: starting (pid=3, poll=100 ticks)
advisord: pid=4 name=spin  NORMAL -> CPU_BOUND (prio 10 -> 4)
advisord: pid=5 name=make  NORMAL -> BATCH     (prio 10 -> 15)
```

**priors 화면:**
```
$ priors
name       class      quantum  samples
spin       CPU_BOUND  4        12
make       BATCH      8        7
sh         NORMAL     1        31
```

**설명 멘트:**

> "왼쪽이 advisord 실행 결과입니다. spin의 priority가 10에서 4로 낮아졌는데, xv6는 숫자가 낮을수록 먼저 실행되기 때문에 이제 spin이 다른 프로세스보다 CPU를 먼저 할당받습니다. [01] 이 결정은 프로세스 이름이 확정되는 exec() 시점에 바로 이루어지고, [02] 클래스에 따라 quantum도 달라져서 spin은 길게, sh는 짧게 CPU를 씁니다. [03] 오른쪽은 이름별로 누적된 학습 데이터로, 이 테이블 덕분에 같은 프로그램이 다시 실행될 때 관찰 없이 즉시 분류됩니다. [04]"

---

## 2페이지 — fbomb + crashme (40초)

**스크린샷 배치:** 화면 좌우 또는 상하로 두 장 나란히

**fbomb 화면:**
```
$ fbomb
fbomb: job group=6, forks succeeded=15 (per-job cap=16)
fbomb: PASS - job was capped, system not exhausted
$ ls        ← 셸이 살아있음
```

**crashme 화면:**
```
$ crashme
@@PANIC oom: kalloc returned 0
@@EV NOTE  pid=4 name=cc   "build: pipeline start"
@@EV EXIT  pid=5 name=cc   run=120 sleep=8
@@EV FORKFAIL pid=4 name=cc group=6 count=16
@@EV NOTE  pid=4 name=cc   "fork rate exploding"
```

**설명 멘트:**

> "왼쪽은 프로세스가 자기 자신을 무한히 복제하는 공격입니다. 연관된 프로세스들은 같은 group_id로 묶이고, [05] 그룹 안의 수가 16개를 넘으면 해당 그룹만 차단됩니다. PASS 아래에 ls가 정상 동작하는 걸 보면 셸은 영향을 받지 않습니다. [06] 오른쪽은 의도적으로 panic을 발생시킨 결과입니다. 커널이 사전에 기록해둔 이벤트 타임라인이 출력되고, 이걸 LLM이 분석해서 원인을 자연어로 설명합니다. [07]"

## 마무리 (10초)

> "7가지 항목 모두 구현 및 실행을 확인했습니다."

---

## 스크린샷 찍는 순서

1. QEMU 부팅 → `advisord` 실행 → `spin`, `make` 실행 → 로그 출력 캡처
2. 같은 세션에서 `priors` 실행 → 테이블 출력 캡처
3. 새로 부팅 → `fbomb` 실행 → PASS + `ls` 정상 동작 캡처
4. 같은 세션에서 `crashme` 실행 → @@PANIC 타임라인 캡처
