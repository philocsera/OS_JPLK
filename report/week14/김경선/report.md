## 비교 요약표

| 문제 | xv6 (기본) | 현대 OS | LLM 어드바이저 (xv6-process 구현) |
|------|-----------|---------|----------------------------------|
| 누가 다음으로 실행 | 도착 순서(FIFO) | 우선순위 등급 | 이름 보고 즉시 분류 |
| 자식 프로세스 분류 | 부모 우선순위 그대로 복사 | 일해본 뒤 판단 | exec() 이름 보고 즉시 분류 |
| quantum 길이 | 전원 1틱 고정 | 등급별 차등(고정값) | 프로세스별 맞춤 추론 |
| 종료 통계 활용 | 전부 휘발 | 로그 쌓지만 자동 활용 안 함 | 이름별 누적 학습 → 다음에 반영 |

| 시스템 panic 진단 | `panic: trap` + 레지스터 숫자 | 메모리 전체 덤프(BSOD) | 이벤트 타임라인 → LLM 자연어 진단 |

## 항목별 설명

### 01. 누가 다음으로 실행되나

CPU는 한 번에 하나의 프로세스만 실행할 수 있다. 여러 프로세스가 동시에 실행을 기다릴 때 누구한테 먼저 CPU를 줄지가 문제다.

> **개념 — 선점(Preemption):** OS가 실행 중인 프로세스를 강제로 멈추고 다른 프로세스에게 CPU를 넘기는 것. 타이머 인터럽트가 발생할 때마다 스케줄러가 "지금 실행 중인 프로세스를 계속 둘지, 다른 걸로 바꿀지" 결정한다. 선점이 없으면 한 프로세스가 CPU를 자발적으로 내놓을 때까지 다른 프로세스는 기다려야만 한다.

**xv6** — 먼저 도착한 순서대로(FIFO) 실행한다. 셸도 줄 맨 뒤에 서야 해서, 앞에 무거운 작업이 쌓여 있으면 사용자 입력에 반응이 한참 뒤에 온다.

**현대 OS** — 우선순위 줄을 여러 단계로 나눈다(HIGH / MID / LOW). 셸처럼 사용자와 대화하는 프로세스는 HIGH 줄로 자동 승격되어 항상 빠르게 응답할 수 있다.

**LLM 어드바이저** — 프로세스가 실행을 시작하기 전, 이름표(make, sh, cc 등)만 보고 즉시 등급을 부여한다. 현대 OS가 실행 이후 행동을 관찰해서 등급을 정하는 것과 달리, 줄을 서기 전부터 이미 등급이 결정되어 있다.

> **비유:** 식당에서 손님을 받을 때 xv6는 도착 순서대로, 현대 OS는 "예약 손님 먼저", LLM 어드바이저는 손님 이름을 보고 문 앞에서 바로 자리를 안내한다.

### 02. 새로 만들어진 자식 프로세스를 어떻게 분류하나

프로그램은 `fork()`로 자기 자신을 복제해서 자식 프로세스를 만든다. 자식은 부모와 다른 일을 하게 되는데, 이 자식을 어떻게 분류할지가 문제다.

> **개념 — fork()와 exec()의 차이:**
> - `fork()` — 현재 프로세스를 통째로 복제한다. 복제 직후 부모와 자식은 완전히 동일한 상태다.
> - `exec()` — 현재 프로세스의 내용을 새 프로그램으로 완전히 덮어쓴다. 이름이 바뀌는 것도 이 시점이다.
>
> 셸이 `make`를 실행하는 순서: `fork()`로 자식 생성 → 자식이 `exec("make")`로 make 프로그램으로 변신.  
> LLM 어드바이저가 분류를 결정하는 시점은 바로 `exec()` 직후 — 이름이 확정되는 그 순간.

**xv6** — 아무 판단 없이 부모의 우선순위를 그대로 복사한다. 자식이 실제로 어떤 일을 할지는 전혀 고려하지 않는다.

**현대 OS** — 자식이 실제로 일하는 모습을 몇 초간 관찰한 뒤에 등급을 정한다. 정확하지만 관찰이 끝나기 전까지는 잘못된 등급으로 동작하는 구간이 존재한다.

**LLM 어드바이저** — `exec("make")`를 호출하는 순간 이름만 보고 즉시 BATCH로 분류한다. 관찰이 필요 없으므로 오분류 구간이 거의 없다.

> **비유:** 신입 직원을 배치할 때 xv6는 "전임자랑 같은 자리", 현대 OS는 "며칠 일해보고 적성 파악 후 배치", LLM 어드바이저는 "이력서(이름) 보고 첫날부터 적합한 자리에 배치".

---

### 03. 한 번 실행될 때 얼마나 오래 CPU를 주나

한 프로세스가 CPU를 너무 오래 독점하면 다른 프로세스가 기다려야 한다. 반대로 너무 자주 교체하면 교체 비용이 누적된다. 그래서 "한 번에 최대 N초"라는 규칙, 즉 quantum을 정한다.

> **개념 — 컨텍스트 스위치(Context Switch):** 프로세스를 교체할 때 OS가 현재 프로세스의 CPU 상태(레지스터 값, 프로그램 카운터, 스택 포인터 등)를 메모리에 저장하고, 다음 프로세스의 상태를 불러오는 작업. 이 과정 자체는 실제 일을 하지 않는 순수 오버헤드다. quantum이 짧을수록 교체가 잦아지고 컨텍스트 스위치 비용이 늘어나고, quantum이 길수록 다른 프로세스의 대기 시간이 길어진다.

**xv6** — 누구든 1틱(0.1초)만 쓰고 무조건 CPU를 반납한다. 공평하지만 긴 계산도 0.1초마다 끊겨서 비효율적이다.

**현대 OS** — 포그라운드는 짧게, 백그라운드는 길게 등 등급별로 다른 quantum을 설정한다. 단, 기본값은 사람이 미리 정해둔 평균치다.

**LLM 어드바이저** — 각 프로세스의 성격을 추론해서 맞춤 quantum을 설정한다. sh는 1틱(즉응), cc는 4틱, 대량 빌드는 8틱처럼 프로세스별로 최적값을 추론한다.

> **비유:** 화구 사용 시간을 xv6는 "전원 5분", 현대 OS는 "VIP 10분, 일반 3분(고정)", LLM 어드바이저는 "김치찌개 15분, 계란후라이 2분"처럼 메뉴별로 맞춤 설정.

### 04. 프로세스가 끝난 뒤 그 기록은?

모든 프로세스는 언젠가 종료된다. CPU를 얼마나 썼는지, 어떤 패턴으로 동작했는지 기록이 남는다. 이 경험을 어떻게 처리하느냐에 따라 다음 실행에 영향을 줄 수 있다.

**xv6** — 부모 프로세스가 `wait()`을 호출하는 순간 자식의 모든 통계가 즉시 삭제된다. 다음에 참고할 방법이 없다.

**현대 OS** — Windows의 ETW, Linux의 /proc 등에 방대한 로그를 저장한다. 하지만 다음에 같은 프로그램이 실행될 때 자동으로 반영되지 않는다. 사람이 직접 분석해야 한다.

**LLM 어드바이저** — 프로세스가 종료될 때 이름별 prior 테이블에 CPU 사용 패턴을 누적 저장한다. 다음에 같은 이름의 프로세스가 실행되면 첫 순간부터 이 경험이 반영된다.

> **비유:** 퇴사한 직원의 기록을 xv6는 바로 버리고, 현대 OS는 창고에 쌓아두지만 아무도 꺼내보지 않으며, LLM 어드바이저는 신입 채용 때 실제로 참고한다.

---

### 05. 프로세스들이 한 팀이라는 걸 아나

실제 작업은 여러 프로세스가 협력해서 이뤄진다. 코드를 빌드할 때 "셸 → make → cc → ld" 순서로 프로세스가 이어지며, 이 전체가 하나의 작업이다. 매니저가 이 "팀" 관계를 인식할 수 있는가가 문제다.

> **개념 — cgroup(Control Group):** Linux에서 프로세스들을 하나의 그룹으로 묶어 CPU, 메모리 등의 리소스를 그룹 단위로 제한하거나 관리하는 기능. "빌드 그룹 전체가 CPU의 30% 이상 쓰지 못하게" 같은 정책을 적용할 수 있다. Windows의 Job Object도 같은 역할이다. 단, 이 그룹은 사람이 수동으로 만들어야 한다.

**xv6** — 각 프로세스는 자기 부모가 누구인지(ppid)만 기록한다. sh, make, cc는 각각 무관한 프로세스로 취급된다.

**현대 OS** — cgroup, Job Object 같은 팀 묶기 기능을 제공하지만, 사람이 직접 만들고 등록해야 한다.

**LLM 어드바이저** — sh → make → cc로 이어지는 흐름을 이름과 트리 구조로 보고 "이건 빌드 작업이구나"라고 자동으로 인식한다. 팀 전체에 같은 정책을 일괄 적용할 수 있다.

> **비유:** xv6는 직원이 누구 밑에 있는지만 알고, 현대 OS는 "빌드팀" 표지판을 누군가 붙여줘야 인식하며, LLM 어드바이저는 업무 흐름을 보고 같은 팀임을 알아서 파악한다.

### 06. fork bomb(무한 복제 공격)을 어떻게 막나

fork bomb은 프로세스가 자기 자신을 끊임없이 복제하는 공격이다. 1초 만에 수천 개의 프로세스가 생겨 시스템 전체가 마비된다. 버그로 의도치 않게 발생하기도 한다.

> **개념 — NPROC / rlimit:**
> - `NPROC` — xv6에서 동시에 존재할 수 있는 프로세스의 최대 개수. 커널 컴파일 시 고정값으로 정해진다(기본 64).
> - `rlimit` — Linux에서 사용자 또는 프로세스별로 리소스 상한을 거는 커널 기능. `ulimit -u 500`으로 생성 가능한 프로세스 수를 제한한다.
> - `pids.max` — cgroup 단위로 프로세스 수를 제한하는 Linux 커널 설정.
>
> 공통점: 모두 **숫자**로만 막는다. 정상 작업인지 공격인지는 판단하지 못한다.

**xv6** — NPROC 한도에 도달할 때까지 아무런 제한 없이 허용한다. 한도가 차야 비로소 거부하는데, 그때는 이미 시스템이 포화 상태다.

**현대 OS** — rlimit, pids.max로 숫자 한도를 걸어둔다. 숫자를 넘으면 막지만, 정상 작업인지 공격인지는 판단하지 못한다.

**LLM 어드바이저** — 정상 빌드 트리와 fork bomb 트리는 모양이 다르다. 이름과 트리 패턴을 보고 "이건 의심스러운 패턴이다"를 감지해서 숫자 한도 전에 미리 차단할 수 있다.

> **비유:** xv6는 식당이 꽉 차야 입장 거부, 현대 OS는 "한 팀 최대 10명" 규칙, LLM 어드바이저는 문 앞에서 단체로 우르르 들어오는 행동 자체를 보고 의심한다.

### 07. 시스템이 멈췄을 때(panic) 뭘 남기나

시스템이 치명적인 오류로 멈추는 것을 panic이라고 한다. Windows의 블루스크린(BSOD), Mac의 커널 패닉이 이에 해당한다.

> **개념 — xv6 panic 시 출력되는 레지스터:**
> - `scause` — 트랩 발생 원인 코드. 예: `0xd`는 "load page fault(잘못된 메모리 읽기)".
> - `sepc` — 트랩 발생 순간의 프로그램 카운터. 어떤 명령어를 실행하다 멈췄는지 가리키는 주소.
> - `stval` — 트랩 관련 추가 정보. page fault라면 잘못 접근한 메모리 주소가 담긴다.
>
> 이 세 값으로 원인을 파악하려면 objdump로 커널을 역어셈블해서 sepc 주소를 직접 찾아가야 한다. 일반 사용자는 해석 불가.

**xv6** — `panic: trap`과 레지스터 숫자 몇 개를 출력하고 멈춘다. 전문가만 해석 가능하다.

**현대 OS** — RAM 전체를 덤프(BSOD, kdump)한다. 정보는 풍부하지만 전문 분석 도구와 전문가 없이는 해독이 불가능하다.

**LLM 어드바이저** — 멈추기 전까지의 시계열 기록을 분석해서 자연어로 진단한다. 예: "5분 전부터 cc가 메모리를 계속 늘렸고, 한계를 초과한 시점에 멈췄습니다. cc의 메모리 누수가 의심됩니다." 최종 판단과 수정은 사람이 한다.

> **비유:** xv6는 의사가 "병났음"만 말하고, 현대 OS는 전신 CT를 찍어두지만 의사가 직접 읽어야 하며, LLM 어드바이저는 CT 옆에서 원인을 풀어 설명해주는 통역사다.

## xv6-process 핵심 구현 방법

> 위 7가지 개념이 `xv6-process/`에 실제로 어떻게 코드로 구현되어 있는지 정리.  
> `advisord` — 백그라운드에서 프로세스 테이블을 주기적으로 읽어 class와 quantum을 조정하는 사용자 프로그램. LLM 어드바이저 역할을 실제로 수행한다.

---

### 01. 스케줄러 선택 — priority + class 기반 best-pick

```c
// proc.c - scheduler()
struct proc *best = 0;
for each proc:
    if RUNNABLE && priority < best->priority → best = p
```

RUNNABLE 프로세스 중 `priority` 값이 가장 낮은(= 가장 중요한) 프로세스를 선택해 실행한다.  
`class_id` 필드로 프로세스 종류(NORMAL / INTERACTIVE / CPU_BOUND / BATCH)를 구분하며, 클래스별 기본 quantum이 다르게 설정된다.

---

### 02. 자식 프로세스 분류 — exec() 시 이름별 prior 자동 적용

```c
// exec.c - kexec()
safestrcpy(p->name, last, sizeof(p->name));  // 이름 확정
proc_seed_from_prior(p);                      // 이전 실행 기록으로 class/quantum 즉시 세팅
```

`exec()` 호출 순간 이름이 확정되고, `proc_seed_from_prior()`가 이전 실행 기록을 조회해 class와 quantum을 즉시 적용한다. "처음 몇 초간 오분류" 구간이 없어진다.

---

### 03. quantum — 프로세스별 맞춤 타임슬라이스

```c
// trap.c - usertrap()
if(p->slice_used >= p->quantum_ticks)
    yield();   // quantum 소진 시 CPU 반납
```

타이머 인터럽트가 올 때마다 `slice_used`를 증가시킨다. 프로세스마다 `quantum_ticks`가 다르게 설정되어 있어 sh는 짧게, cc·make는 길게 CPU를 쓴다. `advisord`가 `setquantum(pid, n)` syscall로 이 값을 조정한다.

---

### 04. 종료 통계 — 이름별 prior 누적 저장

```c
// proc.c - exit()
proc_learn_on_exit(p);   // 이름별 prior 테이블에 CPU 패턴 저장
```

프로세스가 종료될 때 `proc_learn_on_exit()`가 이름, `run_ticks`, `sleep_ticks`를 prior 테이블에 누적한다. 다음에 같은 이름의 프로세스가 `exec()`되면 02번의 `proc_seed_from_prior()`가 이 기록을 읽어 즉시 반영한다.

---

### 05. 프로세스 트리 — group_id로 팀 묶기

```c
// proc.h
int group_id;   // fork 시 부모 group_id 상속
                // setjob()으로 새 그룹 리더 지정 가능
```

`fork()` 시 자식이 부모의 `group_id`를 그대로 상속한다. sh → make → cc로 이어지는 빌드 트리는 모두 같은 `group_id`를 가지게 된다. `advisord`가 그룹 전체에 같은 정책(우선순위·클래스)을 일괄 적용할 수 있다.

---

### 06. fork bomb 방어 — 그룹 단위 프로세스 수 제한

```c
// param.h
#define GROUP_PROC_LIMIT 16   // 그룹당 최대 프로세스 수

// proc.c - fork()
if(p->group_id != 1){
    int gc = proc_group_count(p->group_id);
    if(gc >= GROUP_PROC_LIMIT)
        return -1;   // fork 거부
}
```

한 그룹의 프로세스 수가 16개를 넘으면 `fork()`를 거부한다. 폭주하는 그룹만 차단되고 다른 그룹(sh, init, advisord)은 정상 동작한다. `group_id = 1`인 init은 예외처리되어 시스템 안정성을 보장한다.

---

### 07. panic 진단 — 이벤트 링버퍼 + 호스트 LLM 자연어 진단

```c
// proc.c - 이벤트 종류
EV_NOTE     // 사용자 프로그램이 남긴 메모
EV_EXIT     // 프로세스 종료 (run/sleep 통계 포함)
EV_FORKFAIL // fork 거부 (그룹 한도 초과)
EV_CLASS    // 클래스 변경

// printf.c - panic() 내부
eventlog_dump(s);   // panic 발생 시 타임라인 자동 출력
```

커널은 주요 이벤트를 순환 링버퍼에 계속 기록한다. panic이 발생하면 `eventlog_dump()`가 `@@PANIC / @@EV` 형식으로 타임라인을 출력한다. 호스트의 `tools/diagnose.py`가 이 출력을 LLM에 전달하면 자연어 진단이 생성된다.

---

## 전체 결론

**xv6** — 아무 정보도 안 보고 순서대로. 단순하고 깨지지 않지만 똑똑하지 않음.

**현대 OS** — 일하는 모습을 관찰한 뒤 판단. 정교하지만 ① 처음 몇 초 오분류 ② 경험 자동 재활용 안 됨 ③ 팀 묶기는 수동.

**LLM 어드바이저** — 이름과 의미를 보고, 일하기 전부터 분류. 경험을 학습해서 다음에 활용. 현대 OS의 행동 관찰을 대체하는 게 아니라, **행동을 보기 전의 의미 정보**를 추가로 활용하는 것.

> 세 방식은 경쟁이 아니라 **'덮어쓰기' 관계** — 뒤로 갈수록 앞 방식 위에 새로운 차원을 얹는다.
