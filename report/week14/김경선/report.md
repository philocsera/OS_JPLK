# 스케줄러 3종 비교 — xv6 vs 현대 OS vs LLM 어드바이저

> 출처: `report/week13/조현성/process_summary.html`

---

## 핵심 용어 정리

| 용어 | 뜻 | 비유 |
|------|-----|------|
| **프로세스** | 실행 중인 프로그램 하나 | 주방 요리사 한 명 |
| **CPU** | 실제 계산하는 부품 | 주방 화구(가스레인지) |
| **스케줄러** | 누가 CPU를 쓸지 결정하는 주체 | 주방장(매니저) |
| **셸(Shell)** | 사용자와 대화하는 창구 | 홀 매니저 — 손님 부르면 즉시 응답해야 함 |
| **fork** | 프로세스가 자기 자신을 복제 | 요리사가 자신을 한 명 더 만드는 것 |
| **quantum** | 한 프로세스가 CPU를 연속으로 쓸 수 있는 최대 시간 | "너 5분 쓰고 비켜" |

---

## 비교 요약표

| 문제 | xv6 | 현대 OS | LLM 어드바이저 |
|------|-----|---------|---------------|
| 누가 다음으로 실행 | 도착 순서(FIFO) | 우선순위 등급 | 이름 보고 즉시 분류 |
| 자식 프로세스 분류 | 부모 우선순위 그대로 복사 | 일해본 뒤 판단 | exec() 이름 보고 즉시 분류 |
| quantum 길이 | 전원 1틱 고정 | 등급별 차등(고정값) | 프로세스별 맞춤 추론 |
| 종료 통계 활용 | 전부 휘발 | 로그 쌓지만 자동 활용 안 함 | 이름별 누적 학습 → 다음에 반영 |
| 프로세스 트리 인식 | 부모 포인터만 있음 | 수동으로 cgroup 등록 | 이름+트리 모양으로 자동 묶기 |
| fork bomb 방어 | 한도 찰 때까지 무방어 | 숫자 한도(rlimit) | 트리 모양 패턴으로 의심 탐지 |
| 시스템 panic 진단 | `panic: trap` + 레지스터 숫자 | 메모리 전체 덤프(BSOD) | 시계열 분석 → 자연어로 원인 설명 |

## 항목별 설명

### 01. 누가 다음으로 실행되나

**xv6** — 먼저 도착한 순서대로. 셸이 끼어들고 싶어도 줄 맨 뒤에 서야 해서 응답이 느림.

**현대 OS** — 우선순위 줄을 나눔. 셸처럼 사용자 응답이 필요한 프로세스는 HIGH 줄로 자동 승격.

**LLM 어드바이저** — 이름표(make, sh, cc)를 보는 순간 "이건 빌드용, 이건 대화용" 하고 분류. 줄을 서기 전에 이미 등급이 정해짐.

---

### 02. 새로 만들어진 자식 프로세스를 어떻게 분류하나

**xv6** — 아무 생각 없이 부모 우선순위를 그대로 복사.

**현대 OS** — 자식이 실제로 일하는 모습(CPU 얼마나 쓰는지, 언제 쉬는지)을 관찰한 뒤 분류. 정확하지만 처음 몇 초간 잘못 분류된 채로 동작함.

**LLM 어드바이저** — 자식이 `exec("make")`를 부르는 순간 이름만 보고 즉시 BATCH 분류. 오분류 구간이 거의 없음.

---

### 03. 한 번 실행될 때 얼마나 오래 CPU를 주나

**xv6** — 누구든 1틱(0.1초)만 쓰고 무조건 비킴. 공평하지만 긴 계산도 1틱마다 끊겨서 비효율적.

**현대 OS** — 포그라운드는 짧게, 백그라운드는 길게 등 등급별로 다르게 줌. 다만 기본값은 사람이 미리 정해둔 평균치.

**LLM 어드바이저** — sh는 1틱, cc는 4틱, 대량 빌드는 8틱처럼 각 프로세스 성격에 맞춰 추론해서 설정.

---

### 04. 프로세스가 끝난 뒤 그 기록은?

**xv6** — 부모가 `wait()` 하는 순간 모든 통계 즉시 삭제. 아무것도 남지 않음.

**현대 OS** — ETW(Windows), /proc(Linux) 등에 로그는 쌓임. 하지만 다음에 같은 프로그램이 실행될 때 자동으로 반영되지는 않음. 사람이 따로 분석해야 함.

**LLM 어드바이저** — "make는 평균 이런 패턴이었다"를 이름별로 저장. 다음에 make가 또 실행되면 첫 순간부터 올바른 분류로 시작.

---

### 05. 프로세스들이 한 팀이라는 걸 아나

**xv6** — 각 프로세스가 부모가 누구인지만 기록. 전체가 한 작업이라는 개념 없음.

**현대 OS** — cgroup, Job Object 같은 팀 묶기 기능이 있지만, 사람이 직접 만들고 등록해야 함.

**LLM 어드바이저** — sh → make → cc 흐름을 보면 "이거 빌드 작업이구나" 하고 자동으로 인식. 팀 전체에 같은 정책을 일괄 적용.

---

### 06. fork bomb(무한 복제 공격)을 어떻게 막나

**xv6** — NPROC(최대 64개) 한도 찰 때까지 그냥 받아줌. 한도가 차야 비로소 거부.

**현대 OS** — "이 사용자는 최대 500개" 같은 숫자 한도(rlimit, pids.max) 설정. 하지만 이게 정상 작업인지 공격인지는 판단 못 함.

**LLM 어드바이저** — 정상적인 빌드 트리와 폭주하는 복제 트리는 모양이 다름. 이름과 트리 패턴을 보고 "이건 의심스럽다"고 미리 감지해서 격리 가능.

---

### 07. 시스템이 멈췄을 때(panic) 뭘 남기나

**xv6** — `panic: trap`과 레지스터 숫자 몇 개. 전문가만 해석 가능.

**현대 OS** — RAM 전체를 덤프(BSOD, kdump). 정보는 풍부하지만 분석 도구와 전문가 없이는 읽을 수 없음.

**LLM 어드바이저** — 죽기 전 시계열 기록을 분석해서 "5분 전부터 cc가 메모리를 계속 늘렸고, 한계 초과 시점에 멈췄어요. cc 메모리 누수 의심" 같은 자연어 진단 제공. 결정은 여전히 사람이 함.

---

## 전체 결론

**xv6** — 아무 정보도 안 보고 순서대로. 단순하고 깨지지 않지만 똑똑하지 않음.

**현대 OS** — 일하는 모습을 관찰한 뒤 판단. 정교하지만 ① 처음 몇 초 오분류 ② 경험 자동 재활용 안 됨 ③ 팀 묶기는 수동.

**LLM 어드바이저** — 이름과 의미를 보고, 일하기 전부터 분류. 경험을 학습해서 다음에 활용. 현대 OS의 행동 관찰을 대체하는 게 아니라, **행동을 보기 전의 의미 정보**를 추가로 활용하는 것.

> 세 방식은 경쟁이 아니라 **'덮어쓰기' 관계** — 뒤로 갈수록 앞 방식 위에 새로운 차원을 얹는다.
