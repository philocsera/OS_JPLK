# 스케줄러 3종 비교 — xv6 vs 현대 OS vs LLM 어드바이저

## 핵심 용어 정리

| 용어 | 뜻 | 비유 |
|------|-----|------|
| **프로세스** | 실행 중인 프로그램 하나 | 주방 요리사 한 명 |
| **CPU** | 실제 계산하는 부품 | 주방 화구(가스레인지) |
| **스케줄러** | 누가 CPU를 쓸지 결정하는 주체 | 주방장(매니저) |
| **셸(Shell)** | 사용자와 대화하는 창구 | 홀 매니저 — 손님 부르면 즉시 응답해야 함 |
| **fork** | 프로세스가 자기 자신을 복제 | 요리사가 자신을 한 명 더 만드는 것 |
| **quantum** | 한 프로세스가 CPU를 연속으로 쓸 수 있는 최대 시간 | "너 5분 쓰고 비켜" |

## 비교 요약표

| 문제 | xv6 | 현대 OS | LLM 어드바이저 |
|------|-----|---------|---------------|
| 누가 다음으로 실행 | 도착 순서(FIFO) | 우선순위 등급 | 이름 보고 즉시 분류 |
| 자식 프로세스 분류 | 부모 우선순위 그대로 복사 | 일해본 뒤 판단 | exec() 이름 보고 즉시 분류 |
| quantum 길이 | 전원 1틱 고정 | 등급별 차등(고정값) | 프로세스별 맞춤 추론 |
| 종료 통계 활용 | 전부 휘발 | 로그 쌓지만 자동 활용 안 함 | 이름별 누적 학습 → 다음에 반영 |
| 프로세스 트리 인식 | 부모 포인터만 있음 | 수동으로 cgroup 등록 | 이름+트리 모양으로 자동 묶기 |
| fork bomb 방어 | 한도 찰 때까지 무방어 | 숫자 한도(rlimit) | 트리 모양 패턴으로 의심 탐지 |
| 시스템 panic 진단 | `panic: trap` + 레지스터 숫자 | 메모리 전체 덤프(BSOD) | 시계열 분석 → 자연어로 원인 설명 |

## 항목별 설명

### 01. 누가 다음으로 실행되나

CPU는 한 번에 하나의 프로세스만 실행할 수 있다. 여러 프로세스가 동시에 실행을 기다릴 때 누구한테 먼저 CPU를 줄지가 문제다.

**xv6** — 먼저 도착한 순서대로(FIFO) 실행한다. 매니저가 줄을 보고 맨 앞에 있는 사람을 시키는 방식이다. 문제는 셸(사용자 입력을 받는 프로세스)도 그냥 줄 맨 뒤에 서야 한다는 것이다. 앞에 무거운 작업이 쌓여 있으면 사용자가 키를 눌러도 반응이 한참 뒤에 온다.

**현대 OS** — 우선순위 줄을 여러 단계로 나눈다(HIGH / MID / LOW). 셸처럼 사용자와 대화하는 프로세스는 HIGH 줄로 자동 승격된다. HIGH 줄이 비어야 MID, LOW를 처리하므로 셸은 항상 빠르게 응답할 수 있다.

**LLM 어드바이저** — 프로세스가 실행을 시작하기 전, 이름표(make, sh, cc 등)만 보고 "이건 빌드용 → 백그라운드", "이건 대화용 → 높은 우선순위"로 즉시 분류한다. 현대 OS가 실행 이후 행동을 관찰해서 등급을 정하는 것과 달리, 줄을 서기 전부터 이미 등급이 결정되어 있다.

> **비유:** 식당에서 손님을 받을 때 xv6는 도착 순서대로, 현대 OS는 "예약 손님 먼저", LLM 어드바이저는 손님 이름을 보고 문 앞에서 바로 자리를 안내한다.

---

### 02. 새로 만들어진 자식 프로세스를 어떻게 분류하나

프로그램은 `fork()`로 자기 자신을 복제해서 자식 프로세스를 만든다. 예를 들어 브라우저가 새 탭을 열거나, 셸이 명령어를 실행할 때 이 과정이 일어난다. 자식은 부모와 다른 일을 하게 되는데, 매니저 입장에서 이 자식을 어떻게 분류할지가 문제다.

**xv6** — 아무 판단 없이 부모의 우선순위를 그대로 복사한다. 자식이 실제로 어떤 일을 할지는 전혀 고려하지 않는다.

**현대 OS** — 자식이 실제로 일하는 모습, 즉 CPU를 얼마나 쓰는지, 언제 쉬는지를 몇 초간 관찰한 뒤에 등급을 정한다. 정확하지만 관찰이 끝나기 전까지는 잘못된 등급으로 동작하는 구간이 존재한다. 이 구간 동안 중요한 작업이 낮은 우선순위로 처리될 수 있다.

**LLM 어드바이저** — 자식이 `exec("make")`를 호출하는 순간, 즉 "나 이제부터 make를 실행할 거야"라고 선언하는 그 순간에 이름만 보고 즉시 BATCH(백그라운드 작업)로 분류한다. 관찰이 필요 없으므로 오분류 구간이 거의 없다.

> **비유:** 신입 직원을 배치할 때 xv6는 "전임자랑 같은 자리", 현대 OS는 "며칠 일해보고 적성 파악 후 배치", LLM 어드바이저는 "이력서(이름) 보고 첫날부터 적합한 자리에 배치".

---

### 03. 한 번 실행될 때 얼마나 오래 CPU를 주나

한 프로세스가 CPU를 너무 오래 독점하면 다른 프로세스가 기다려야 한다. 반대로 너무 자주 교체하면 교체 비용(컨텍스트 스위치)이 누적된다. 그래서 "한 번에 최대 N초"라는 규칙, 즉 quantum을 정한다.

**xv6** — 누구든 1틱(0.1초)만 쓰고 무조건 CPU를 반납한다. 공평하지만, 긴 계산을 하는 프로세스도 0.1초마다 끊겨서 자리를 바꿔야 하므로 비효율적이다. 컨텍스트 스위치가 필요 이상으로 자주 발생한다.

**현대 OS** — 포그라운드(현재 화면에 보이는 앱)는 짧게, 백그라운드는 길게 등 등급별로 다른 quantum을 설정한다. 단, 이 기본값은 사람이 미리 정해둔 평균치라 모든 상황에 최적이지는 않다.

**LLM 어드바이저** — 각 프로세스의 성격을 추론해서 맞춤 quantum을 설정한다. 예를 들어 sh(대화형)는 1틱으로 짧게 줘서 응답성을 높이고, cc(컴파일러)는 4틱, 대량 빌드는 8틱으로 길게 줘서 컨텍스트 스위치를 줄인다. 사람이 미리 규칙을 정하지 않아도 프로세스 이름과 패턴을 보고 스스로 판단한다.

> **비유:** 식당 화구 사용 시간을 xv6는 "전원 5분", 현대 OS는 "VIP 10분, 일반 3분(고정)", LLM 어드바이저는 "김치찌개는 15분, 계란후라이는 2분"처럼 메뉴별로 맞춤 설정.

### 04. 프로세스가 끝난 뒤 그 기록은?

모든 프로세스는 언젠가 종료된다. 그 동안 CPU를 얼마나 썼는지, 메모리를 어떻게 사용했는지, 어떤 패턴으로 동작했는지 기록이 남는다. 이 경험을 어떻게 처리하느냐에 따라 다음 실행에 영향을 줄 수 있다.

**xv6** — 부모 프로세스가 `wait()`을 호출하는 순간 자식의 모든 통계가 즉시 삭제된다. 그 프로세스가 무엇을 했는지 다음에 참고할 방법이 없다.

**현대 OS** — Windows의 ETW, Linux의 /proc 등을 통해 방대한 양의 로그를 저장한다. 하지만 이 기록이 다음에 같은 프로그램이 실행될 때 자동으로 반영되지는 않는다. 누군가가 직접 분석해서 수동으로 설정을 바꿔야 효과가 있다.

**LLM 어드바이저** — 프로세스가 종료되기 직전, "이 이름의 프로그램은 평균적으로 이런 패턴이었다"를 이름별로 누적 저장한다. 다음에 같은 이름의 프로그램이 실행되면 첫 순간부터 이 경험을 바탕으로 올바른 분류와 quantum을 적용한다.

> **비유:** 퇴사한 직원의 기록을 xv6는 바로 버리고, 현대 OS는 창고에 쌓아두지만 아무도 꺼내보지 않으며, LLM 어드바이저는 신입 채용 때 실제로 참고한다.

---

### 05. 프로세스들이 한 팀이라는 걸 아나

실제 작업은 단일 프로세스가 아니라 여러 프로세스가 협력해서 이뤄지는 경우가 많다. 예를 들어 코드를 빌드할 때 "셸 → make → cc → ld" 순서로 프로세스가 이어지며, 이 전체가 하나의 작업이다. 매니저가 이 "팀" 관계를 인식할 수 있는가가 문제다.

**xv6** — 각 프로세스는 자기 부모가 누구인지(ppid)만 기록한다. 전체가 한 작업이라는 개념 자체가 없다. sh, make, cc는 각각 무관한 프로세스로 취급된다.

**현대 OS** — cgroup(Linux), Job Object(Windows) 같은 팀 묶기 기능을 제공한다. 하지만 사람이 직접 그룹을 만들고 프로세스를 등록해야 한다. 자동으로 인식되지 않는다.

**LLM 어드바이저** — sh → make → cc로 이어지는 흐름을 이름과 트리 구조로 보고 "이건 빌드 작업이구나"라고 자동으로 인식한다. 팀 전체에 "너희는 백그라운드 빌드 팀이니 우선순위 낮춤" 같은 정책을 일괄 적용할 수 있다. 사람이 등록할 필요 없다.

> **비유:** xv6는 직원이 누구 밑에 있는지만 알고, 현대 OS는 "빌드팀" 표지판을 누군가 붙여줘야 인식하며, LLM 어드바이저는 직원 이름과 업무 흐름을 보고 같은 팀임을 알아서 파악한다.

---

### 06. fork bomb(무한 복제 공격)을 어떻게 막나

fork bomb은 프로세스가 자기 자신을 끊임없이 복제하는 공격이다. 복제된 프로세스가 또 복제하고, 또 복제하며 1초 만에 수천 개의 프로세스가 생겨 시스템 전체가 마비된다. 버그로 인해 의도치 않게 발생하기도 한다.

**xv6** — NPROC(기본 64개) 한도에 도달할 때까지 아무런 제한 없이 프로세스 생성을 허용한다. 한도가 차야 비로소 거부하는데, 그때는 이미 시스템이 포화 상태다.

**현대 OS** — rlimit, pids.max 같은 설정으로 "이 사용자는 최대 500개"처럼 숫자 한도를 걸어둔다. 숫자를 넘으면 막지만, 지금 복제되는 프로세스가 정상 빌드 작업인지 공격인지는 판단하지 못한다.

**LLM 어드바이저** — 정상적인 빌드 트리(sh → make → cc 같은 단계적 구조)와 fork bomb의 트리(한 프로세스가 같은 자식을 폭발적으로 복제하는 구조)는 모양이 다르다. 이름과 트리 모양을 보고 "이건 의심스러운 패턴이다"를 감지해서 숫자 한도에 도달하기 전에 미리 강등하거나 격리할 수 있다.

> **비유:** xv6는 식당이 꽉 차야 입장 거부, 현대 OS는 "한 팀 최대 10명" 규칙, LLM 어드바이저는 문 앞에서 단체로 우르르 들어오는 행동 자체를 보고 의심한다.

---

### 07. 시스템이 멈췄을 때(panic) 뭘 남기나

시스템이 치명적인 오류로 멈추는 것을 panic이라고 한다. Windows의 블루스크린(BSOD), Mac의 커널 패닉이 이에 해당한다. 매니저가 죽기 직전에 어떤 정보를 남기느냐에 따라 원인 파악이 쉬울 수도, 어려울 수도 있다.

**xv6** — `panic: trap`이라는 짧은 문자열과 함께 레지스터 값(scause, sepc, stval) 몇 개를 출력하고 멈춘다. 어떤 숫자가 어떤 의미인지 알려면 RISC-V 명세와 xv6 소스를 깊이 아는 사람이어야 해석할 수 있다.

**현대 OS** — 시스템이 멈추는 순간 RAM 전체를 파일로 저장한다(메모리 덤프). 담긴 정보는 매우 풍부하지만 WinDbg, crash 같은 전문 분석 도구와 전문가 없이는 해독이 사실상 불가능하다.

**LLM 어드바이저** — 멈추기 전까지의 시계열 기록(어떤 프로세스가 언제 무엇을 했는지)을 분석해서 자연어로 진단 메시지를 제공한다. 예: "5분 전부터 cc가 메모리를 계속 늘렸고, 한계를 초과한 시점에 시스템이 멈췄습니다. cc의 메모리 누수가 의심됩니다." 단, 최종 판단과 수정은 사람이 한다. AI는 제안만 한다.

> **비유:** xv6는 의사가 "병났음"만 말하고, 현대 OS는 전신 CT를 찍어두지만 의사가 직접 읽어야 하며, LLM 어드바이저는 CT 옆에서 "이 부위가 문제인 것 같습니다"라고 풀어서 설명해주는 통역사다.

---

## 전체 결론

**xv6** — 아무 정보도 안 보고 순서대로. 단순하고 깨지지 않지만 똑똑하지 않음.

**현대 OS** — 일하는 모습을 관찰한 뒤 판단. 정교하지만 ① 처음 몇 초 오분류 ② 경험 자동 재활용 안 됨 ③ 팀 묶기는 수동.

**LLM 어드바이저** — 이름과 의미를 보고, 일하기 전부터 분류. 경험을 학습해서 다음에 활용. 현대 OS의 행동 관찰을 대체하는 게 아니라, **행동을 보기 전의 의미 정보**를 추가로 활용하는 것.

> 세 방식은 경쟁이 아니라 **'덮어쓰기' 관계** — 뒤로 갈수록 앞 방식 위에 새로운 차원을 얹는다.
